# tethr — 設計の整理 02

2026-09-12。これまでの会話と、Devin / DeepSeekへの再相談をまとめた議論用メモ。以下では、ユーザーが明示した用途と、アシスタント側の設計提案を区別する。実装やスタックの確定はまだ行っていない。

## 1. ユーザーが解消したい手間

| 手間 | ユーザーが挙げた内容 |
| --- | --- |
| 単発の用事のために道具を開く | チャット、コーディングエージェント、ターミナル |
| 結果を手で運ぶ | レスポンスをコピーし、次の作業へ貼り付ける |
| 操作を思い出す | コマンドを思い出す |

結果の送り先は、コーディングエージェント、エディタ、検索欄、チャットウィンドウ、Gmail。

具体的な用途には、文章のこまごました推敲、その場での翻訳、エージェントへの指示がある。利用頻度や優先順位はまだ数値化していない。

以前からの方向性も維持する。terminalとの境界をなくす「ハイパーQuake」、個人のGhostty / tmuxワークフローへの統合、DeepSeek Harness連携の検討、Macでの快適さ、開発速度、開発するLLMへの強いフィードバック。名前はtethrが有力候補。

## 2. 用途を横断する設計仮説

**今いる場所から短い用事を始め、必要なら数回調整し、結果を次に使う場所へ届ける。**

これは親側の整理であり、確定した製品定義ではない。

基本の往復は「呼ぶ → 依頼する → 結果を見る／調整する → 使う → 元の作業へ戻る」。素材には選択文、貼り付けたテキスト、端末の出力などがあり、素材なしの質問・コマンド探し・エージェントへの依頼もできる案にする。

### 呼び出し元と送り先を別にする

- Gmailで推敲を呼び、結果を同じ本文へ戻す。
- 端末の出力から依頼を作り、別のエージェント会話へ渡す。
- 翻訳を読み、その一部を検索欄へ持っていく。

呼び出し元が分かっているとき、同じ対象を一覧で探し直す操作を挟まない。別の送り先を使うときは、それを指定できるようにする。具体的な取得・挿入手段は未検証。

### 一つの用事の中で、短い修正を続ける

「少し自然に」→「もっと短く」→「最後の一文は原文に戻す」のような往復を想定する。原文と現在の案を区別し、指示がどの案に適用されたかを保持する。

エージェントへの指示は、書いたまま渡す経路を持つ。推敲を依頼した場合だけ文章を整える。エージェントへの依頼を始める前に、必ず別モデルで指示を加工する構成にはしない。

### 送り先と、そこで行う操作を別にする

| 送り先の例 | 操作の意味 |
| --- | --- |
| Gmail / チャット / エディタ | 選択部分を置き換える、入力欄へ挿入する |
| 検索欄 | 検索語を入れる、検索を開始する |
| エージェントの会話 | 指示の下書きを置く、追加指示として送る |
| ターミナル | コマンド案を編集可能な形で置く、明示したコマンドを実行する |

「どこへ」と「何をするか」を表示と内部処理で区別する。Gmailへ挿入したことをメール送信済みと扱わない。処理結果が不明なときも、成功したと決めつけない。

これを理由に、毎回「採用 → 挿入プレビュー → 再確認」という段階を増やす必要はない。結果を見たうえでの「挿入」など、意味が分かる操作を中心に検討する。

### コマンド想起も同じ入口で扱う

よく使う操作を、短い名前や説明から探せるようにする案。「ポートを使っているプロセスを調べる」など、用事から呼ぶ。

保存する操作には、入力の扱い、処理の種類、依頼文またはコマンド、返し方が必要になる。単に過去のプロンプトを再利用するだけでコマンド操作が完成したとは考えない。具体的な登録形式やAIによる候補生成の範囲は未決定。

## 3. 再相談で得た意見

両者とも、前回の端末→エージェント転送を最初の必須機能とする推奨を見直した。

| 論点 | Devin / SWE-2 Max | OpenCode / DeepSeek V4.1 Flash |
| --- | --- | --- |
| 最初の体験 | 小さな変換を呼び、結果を前のアプリへ返す | 選択文の推敲・翻訳から、元の入力欄への挿入まで |
| 構成 | UIを交換できるよう、変換と返却処理を分ける | 送り先に加え、挿入・送信・実行などの意味と適用状態を持つ |
| TUI | 開発上の利点はあるが、他アプリへの返却の実用性を実機で試す | 画面方式を確定せず、実際の一往復を比較する |
| 後回し | WorkItem、独自復旧、豊富な差分UI、未定義の長期作業引継ぎ | 部分採用、多数の候補、細かな比較UI、新しいDSLやプラグイン基盤 |

Devinは、TUIが他アプリとの文章の往復に適するかを再評価した。TUIでもできる／できないと断定せず、呼び出しと実際の返却が自然に成立するかを試すという提案。

DeepSeekは「端末転送を初回の必須条件にしたのは過剰だった」と明示的に撤回した。今回特に有用なのは、送り先だけでは結果をどう使ったかが分からない、という指摘。

## 4. 親側で採用候補にする点と、修正した点

**採用候補**は、起点の選び直しを減らすこと、実際の送り先まで含めて便利さを確かめること、結果の使い方を区別すること、最初のUIを小さくすること。

一方、外部の意見もそのまま仕様にはしない。

- エージェントは最初から単発の依頼先になれる。Devinの「作業が大きくなったときだけ委譲する」という構成では、明示された用途が狭まる。
- 短文処理でも、原文・現在の案・追加指示の関係は必要。「素材と指示だけ」の関数に切り出しても、その外側で調整中の文脈を持つ責任は残る。
- 素材がない状態からの相談やコマンド探しも残す。選択文が必須の文章編集ツールには限定しない。
- 任意のpaneへ文字を送るだけでは、shell入力なのかエージェントへの指示なのかは確定しない。端末との接続は対象と操作の意味を確認する必要がある。
- 差分・部分採用は親側の提案であり、初回から必須ではない。原文と現在の案を見られる小さな表示から検討できる。ただし変更点の要約だけを正確な比較の代わりにはしない。
- DeepSeekの「時間やキー数を指標にしない」は採らない。現在の方法との比較には使える。根拠のない固定目標を置かず、入力のやり直し・送り先の正しさ・修正の手間と合わせて見る。
- Gmailなどの送り先は挙がっているが、GUI用途が多数派だという頻度の断定はしない。

## 5. 最初の試作案と、残る判断

**推奨する最初の試作は、一つの実際の入力欄で「短文を取り込み → 推敲または翻訳 → 一度追加修正 → 結果を見て元の入力欄へ反映」する往復。**

同じ題材を、現在の「チャットを開く → 貼る → 頼む → コピー → 戻る」と比較する。

確認したいのは、原文を再入力せず調整できること、採用した案が意図した入力位置へ入ること、手作業による結果の運搬を減らせること、戻ったあと自然に編集を続けられること。clipboardへのコピーだけができても、目的の入力欄へ返す部分が未成立なら、その限界を区別する。

最初に対応するアプリと入力欄を一つ明記し、そこでの成功を他アプリ全体の互換性とは扱わない。元の欄へ戻せた次の比較として、呼び出し元と送り先が異なるケースを試す。

端末・エージェント用途を設計から落とさないため、「素材なしで操作を探し、コマンド案を端末で編集できる形に渡す」「指示文を加工せず、選んだエージェント会話へ渡す」も次の小さな確認例として残す。これらを最初の文章往復と同時に全部実装する決定ではない。

スタックは、Bun + TypeScript + OpenTUI/Reactを既存の有力案として残す。まずMac上での呼び出し・日本語入力・選択範囲の取得・結果の返却を確かめ、必要な表示面やMac固有部の範囲を判断する。Swift中心への変更も、TUI固定も、この相談結果だけで確定しない。

短い文章処理、コマンド操作、エージェントへの指示送信を区別して扱えるように考える。DSHは連携候補であり、全処理を必ずDSHに通すと決めてはいない。今回相談に使ったモデルは、製品が使うモデルの決定ではない。

まだ決める必要があるのは、最初に試す実際の一往復、調整中の用事を閉じた後の保持、既知の入力欄へ戻せない場合の扱い、文章処理の接続先、長い作業へ移るときの引継ぎ内容。常駐処理や会話DBは、それらを具体化して必要性を判断する。
