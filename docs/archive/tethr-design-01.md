## 今回の暫定提案

| 呼び出し場面 | 最初にできること | まだ選ぶ必要があること |

| tmuxのpaneから | そのpaneを起点に操作する | 渡す出力範囲、送り先の会話、依頼内容 |

これは操作案。具体的な引数、キー、画面構成、APIは未決定。端末からの呼び出しで対象が特定できない場合も、別のpaneを推測で採用しない。

最初からユーザーに新しい「作業」を登録させるかは保留。まず既存のpaneと会話を別の対象として扱い、必要な関連だけ保持する案を推す。複数paneと会話を、独立した名前を持つ一つの仕事として日常的に扱いたくなった場合は再検討する。

## 外部意見から拾った点と、採用しなかった断定

**Devin:** 作業一覧が出発点であるという前提を疑うべき。目の前のpaneから出力を渡したい場面では、同じpaneを一覧で探し直す操作が余分になる。初回実験は出力転送、WorkItemは保留、という提案。

**DeepSeek:** 検索だけでなく一度の文脈転送まで試すと構想の価値が見えやすい。検索・AI・shellの入力先が曖昧になると既存の単純な道具より悪くなる、という指摘。

**親側の評価:** 対象の選び直しを減らす点、入力先を明確にする点を採用候補にする。一方、検索・復帰だけでもユーザーの痛点に合えば価値はある。「転送を作らなければHyperQuakeではない」という断定は採用しない。

Devinの「検索・復帰にもcapture→send→statusが結局必要」という主張は、検索して対象を開く機能だけには当てはまらない。転送を必須にする根拠にはしない。また、参照切れは軽いリンクにも生じ、WorkItemというデータ構造だけで所有権の二重化が決まるわけではない。

DeepSeekの「会話を選んだらpaneをプレビュー」は、会話とpaneの対応がある前提を追加している。自動で同一視しない。「最後の会話・pane・cwdの3つだけで足りる」「3キー・15秒」という基準も、利用場面や実測で裏づけられていないため採用しない。

## Devinの回答

**1. 最強の隠れた前提**

提案群の根底にあるのは「主問題は作業の発見と帰還であり、tmux/DSH 全体を列挙する一覧面が要る」という前提。行表示派と WorkItem 派は同じ前提の別実装に過ぎない。痛む日常例:tmux pane でテストが落ち、**今見ている pane** の出力を DSH の既存会話に流したい。一覧前提だと「面を開く→行を探す→目の前の pane を再選択→会話選択」となり、発見層が本筋で空回りする。起点は一覧ではなく現在 pane である場面が多分多い。

**2. 最初の縦スライス**

「現在 pane の末尾出力 → DSH 会話(新規/既存)を選んで投入 → 進行状態を機械可読で返す」一本。tmux ポップアップ/キーバインド発火、常駐なし。検証する問い:「摩擦の本体は文脈の境界(手渡し)であり、発見ではないか」。反証:日常的に使った上で依然「何が走っていたか戻れない」が頻発するか、DSH CLI+コピペと大差なく起動理由が消える場合。対抗案(発見と帰還)はこの slice が要する capture→send→status プリミティブを結局必要とし、先に一覧を作るとデーモン誘惑と所有権の二重化が始まる。欠点:発見が真の痛みだった場合の学習が遅い。

**3. WorkItem の扱い**

v0 はバックエンドネイティブ対象(tmux の session:pane、DSH session id)+オプションのリンク記録を仮選択。WorkItem は「仕事とは何か」の所有権を tethr に複製し、pane 死亡時のダングリング、GC、常駐の口実を生む。リンクだけならバックエンドが知らない関連付けだけを保持し、実体の同一性は各バックエンドに残る。逆転シナリオ:`tmux kill-server` や再起動を跨いで「認証修正=2 pane+1 会話」をまとめて復帰したい頻度が高い場合。バックエンド id が全滅する環境では、安定ハンドルとしての WorkItem が逆に必要になる。

**4. 設計を最も変える質問**

「直近1週間で『見失った/戻れなかった』回数と『出力をエージェントに渡すのが面倒だった』回数、具体的にどちらが多かったか?」——この1答が一覧派対転送派、スライス選択、WorkItem 要否を同時に振り分ける。

**未検証の技術的前提(意見と分離)**:DSH に会話列挙・追記・状態取得の外部 API が実在するか、tmux id の再起動後の安定性、Ghostty Quick Terminal 経由の発火手段。いずれもここでは未確認。

## DeepSeekの回答

**1. 30秒の具体像**

ブラウザで記事を読み「このAPI仕様を試したい」と思う。ホットキーでtethr起動。

- 起動時: 記憶されるのは作業文脈ではなく直前フォーカス。検索欄にカーソル、前回の作業を上位数件表示。ブラウザのURL/選択テキストは自動では取り込まない(取り込みは明示)。
- 検索: "dsh"と入力→生存中のエージェント会話とpaneが候補に混在。各行に状態(実行中/待機/終了)、cwd、最終出力1行。
- 選択: 会話を選ぶとpaneをプレビュー。記憶するのは選択した会話IDと直前に見ていたpane。
- 転送: 記事の要点をペースト→送信。ここで送信先会話と送信時cwdを記憶。
- 待機: エージェントが走る。tethrを閉じても会話は生存。
- 復帰: ホットキー→同じ一覧→上位に「さっきの会話(新着あり)」。1キーで出力をブラウザへコピー、または該当paneへ戻る。
- 記憶すべきは「最後の会話」「最後のpane」「最後のcwd」の3つだけ。毎回聞き直さない。

**2. 既存ピッカーより悪くなる最大要因と最小の修正**

最大要因は「何に打ち込んでいるか」の曖昧さ。検索/エージェント/シェルが同一入力欄を共有すると、送信ミスで検索語がエージェントに飛ぶ。単一用途の既存ピッカーでは起きない。
最小修正: 欄は分けず、モード表示を常時1箇所(プロンプト記号)に出す。加えてプレフィックスを1つだけ許す(例: 先頭`=`で検索固定)。これで「今どこに書いているか」が常に見える。

**3. 統一検索/復帰だけでHyperQuakeを検証できるか**

暫定: 不十分。検索/復帰は既存セッションピッカーの延長で、HyperQuake=「ランチャーと端末の摩擦除去」の核心は文脈の持ち越しにある。1つだけ実際の転送(ペイン出力→エージェント会話)を最初の実験に含めるべき。
反証可能な受け入れ観察: 「ブラウザで見つけた文字列を、tethr内で手入力・コピペ往復なしに、生存中の会話へ渡し、応答が同じ画面で見える」までをキー操作3回以内・15秒以内で完了できる。これが無理なら検索/復帰にも価値はあるが、それはHyperQuakeではなく高機能ピッカーと呼ぶべき。

**4. 人間への質問(1つ)**

「普段ブラウザから端末へ渡す情報は、選択テキストのコピペですか、それとも『このURLを調べて』のような指示文ですか?」 — 前者なら転送はクリップボード経由、後者なら入力欄そのものが主役になり、UIの重心が変わります。
