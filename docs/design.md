# tethr — ターミナルを優先する設計方針

2026-09-12。ユーザーの「文章よりもターミナル周りの機能の方が嬉しさが高いので、優先度を上げる」を反映する。これ以降の優先順位と試作の検討はこの文書を基準にする。設計整理02とAstraレビュー03は、それ以前の検討記録として残す。

## 確定した優先順位

**ターミナル周りの機能を先に扱う。アプリケーションのrun-or-raiseも実装対象に含める。文章の推敲・翻訳は、その後に広げる用途として残す。**

特に、以前から明示されていた次の手間を中心に据える。

- 単発の用事のためにターミナルやコーディングエージェントを開く。
- コマンドを思い出す。
- 応答や出力を手でコピーして次の作業へ渡す。

Ghostty / tmuxの個人ワークフローとの統合、DeepSeek Harness連携の検討、Macでの快適さ、開発速度、LLMへのフィードバックも継続する。エージェントへの指示は、ターミナル周りの中心的な用途として扱う。文章の推敲を経由させる必要はない。

## 主軸にする体験の案

**短い端末作業をすぐ始め、必要なコマンドや対象を見つけ、結果を次の操作へつなぐ。**

| 端末で手が止まる場面 | tethrで目指す操作 |
| --- | --- |
| 短い用事をするために窓や作業場所を整える | 呼び出して、対象の作業文脈で始める |
| アプリを開くか、起動済みのアプリを探して戻る | 同じ操作で、未起動なら起動し、起動済みなら前面へ出す（run-or-raise） |
| コマンドやオプションを思い出せない | 用事の名前・説明などから候補を見つけ、内容を見て使う |
| 出力を見て、説明や調査を頼みたくなる | 必要な範囲を選び、対象のエージェントへ依頼と一緒に渡す |
| 続いている端末・エージェントへ戻りたい | 対象を選んで続きを開く、または指示を届ける |

run-or-raiseはユーザーが追加した実装対象。それ以外の具体的な操作は設計案であり、端末機能とrun-or-raiseの中の順位はまだ確定していない。既存paneへの移動、コマンド検索、出力の受け渡し、エージェントへの指示のどれを最初に完成させるかは、別の判断として残す。

## アプリケーションのrun-or-raise

ユーザーの「アプリケーションのrun-or-raiseもやる」を反映する。対象はGhosttyに限らず、一般のMacアプリも含む。

| 対象アプリの状態 | 基本動作 |
| --- | --- |
| 未起動 | 対象アプリを起動して前面へ出す |
| 起動済み | 既存の対象アプリを前面へ出す |
| すでに前面 | そのアプリを引き続き使える状態にする |

アプリを選ぶ同じ操作で、起動と復帰を行えるようにする。既存アプリへ戻る際に、新しいウィンドウや別プロセスを作る操作は要求しない。AIへの問い合わせを経由せず呼べる基本操作として設計する。

アプリ単位のrun-or-raiseと、tmuxの特定pane・エージェントの特定会話への移動は別の対象として扱う。run-or-raiseの確認では、未起動からの起動、起動済みアプリへの復帰、連続して呼んだ場合を試す。複数ウィンドウ、最小化、別のSpace、起動済みでウィンドウがない場合の詳細は、実機での挙動を確認して決める。

## 最初の試作案の変更

以前の「文章を取り込み、推敲して元の入力欄へ返す」試作は後段へ移す。

親側の現時点の提案は、まず **「呼ぶ → 用事からコマンドを探す → 対象の環境で実行する → 結果を読む」** を一つの端末作業で試すこと。その次に、同じ結果を選んだエージェントへ渡す経路を足す。

具体例は、プロジェクトの変更状況を確認する、必要なログを探す、指定ポートの使用状況を調べるなど。どの用事を採用するかはまだ決めていない。既存の作業に戻ることが主な障害なら、最初の試作を対象検索・移動へ寄せる余地もある。

ターミナルが起点のときは、特定できている作業対象を再選択させない案にする。デスクトップから呼ぶときは、対象の作業場所を明確にできる案にする。AIによる候補生成を全操作の前提にはせず、登録済みの操作や履歴を使う範囲も検討する。

コマンド候補の提示、入力行への配置、実行、エージェントへの指示送信は意味を分ける。今回の優先順位変更だけで自動実行やDSH必須化は決めない。同じディレクトリでの新規実行と、既存の対話シェルの続きも同一視しない。

## 試作で確認すること

- 普段の方法と比べ、起動・対象探し・コマンド想起の手間が減るか。
- 意図した対象で操作でき、入力先を見失わないか。
- 出力を次の操作へ使えるか。エージェント連携を試す段階では、手でコピーする往復が減るか。
- 一発で終わる用事を短く済ませられるか。既存の作業を隠す・表示し直す操作が、その作業を不用意に終了させないか。
- 失敗したとき、入力・対象・予定した操作・実際の結果をLLMに返し、修正を再確認できるか。

対象が途中で消えた場合や、paneで動くプログラムが変わった場合も、操作の意味が保たれるかを確認する。細かな実装方法やMac連携の可否は未検証。

## スタックと後段の用途

Ghostty / tmuxを使う操作面と、Bun + TypeScript + OpenTUI/Reactという既存案を、端末作業の試作候補として評価する。採用判断は端末での操作、Macでの呼び出し、日本語入力、LLMが失敗を観測できるかに置く。文章を外部アプリへ挿入する機能は、初期スタックを決める必須試験から外す。

短い文章の推敲・翻訳、Gmailなどの入力欄への返却、豊富な差分表示・部分採用は後段で検討する。端末作業で実際に必要と分かった入力・出力の扱いを、その際に再利用する。

今回までに変更したのは優先順位、試作案、run-or-raiseのスコープ追加。実装開始、最初のコマンド、エージェントの接続方式、常駐構成、言語・ライブラリの正式採用はまだ決めていない。
